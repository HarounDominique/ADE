Este nexus es el índice único de las specs de ADE. Las specs se citan por `module id + heading`, nunca por número de línea.

## Product brief

Assay es una **Agentic Software Engineering Workstation** para el desarrollador individual avanzado que dirige agentes capaces de explorar, modificar y verificar software. El problema que resuelve es la fragmentación entre agente, IDE, terminal, Git, documentación, skills y runtime: ninguna herramienta representa simultáneamente la intención, el contexto, el cambio y su aceptabilidad.

La visión es que el humano dirija intención y restricciones, los agentes ejecuten trabajo y Assay haga observable, verificable, reversible y revisable el resultado. Assay no compite por tener el mejor modelo: organiza el workflow por encima de modelos y runtimes intercambiables.

Éxito inicial significa que el usuario pueda trabajar una semana principalmente dentro de Assay y reducir drásticamente los cambios de contexto. La primera versión es desktop/local-first; el diseño debe poder evolucionar a equipos sin introducir cloud en el MVP.

## Product principles

- **Agent-first:** `Task`, no archivo ni editor, es la unidad principal.
- **Human-in-command:** el humano define intención, restricciones y aceptación.
- **Provider-agnostic:** cambiar de modelo no obliga a cambiar de workflow.
- **Documentation-first:** el conocimiento versionado expresa intención y arquitectura.
- **Verification-first:** el agente no es autoridad sobre su propio resultado.
- **Observable and reversible:** cada operación significativa tiene evidencia, atribución e historial.
- **Progressive autonomy:** permisos y automatización escalan según confianza y riesgo.

## Truth model

| Fuente | Qué representa | No debe sustituirse por |
|---|---|---|
| Código | Verdad ejecutable | Resumen del agente |
| Documentación | Verdad intencional y de diseño | Memoria opaca |
| Git | Verdad histórica | Timeline de ADE |
| Tests y runtime | Evidencia comportamental | Afirmación de “terminado” |
| ADE DB | Historial operativo | Estado del repositorio |
| ASK (futuro) | Evidencia estructural | Juicio humano |

## Tech Foundations

- Producto desktop, local-first y orientado inicialmente a un desarrollador avanzado.
- El dominio se organiza alrededor de `Project → Task → Agent → Change → Verification → Review`.
- OpenCode, Codex y Claude Code son los runtimes locales iniciales, siempre detrás de adapters y del contrato `AgentRuntimePort`.
- Git conserva código, documentación, skills e historial del repositorio.
- SQLite es la opción provisional para metadata operativa de ADE.
- Markdown y configuración versionable son el formato preferente de conocimiento.
- Implementer y Reviewer son roles separados; el reviewer recibe contexto fresco y evidencia.
- Las gates son declarativas y bloquean transiciones cuando una condición requerida falla.
- El workflow de desarrollo es adaptativo: las fases orientan, los gates protegen y los bucles permiten volver al punto que necesita nueva información.
- Tauri 2 es el framework adoptado para el shell desktop; el esquema operativo actual de `.ade/` usa JSON versionable y retrieval semántico sigue diferido.
- ADE es multiplataforma por objetivo: macOS, Windows y Linux. Cada plataforma declara su grado de soporte real —`verificada`, `construible` o `no verificada`— y ningún documento afirma más de lo que CI o un smoke registrado respaldan. El contrato está en [SPEC-cross-platform-support](SPEC-cross-platform-support.md#platform-boundary).

## v0.3 product direction

ADE evoluciona de shell desktop operativa a workspace agéntico local-first. El usuario debe poder abrir un repositorio, navegar su máquina, usar una terminal nativa, seleccionar un proveedor con licencia, ejecutar skills y mantener código y documentación viva dentro del mismo contexto.

La v0.3 prioriza `workspace-core`: sin contexto local navegable y terminal integrada, los demás módulos obligan al usuario a volver a cambiar de aplicación.

## Current implementation baseline

Actualización de contexto (2026-09-06): este contrato sustituye cualquier referencia anterior de esta baseline a una topbar limitada a Project y branch. Incluye `Current task` entre ambos, con las 12 Tasks más recientes por creación, preservación de una selección anterior y sincronización inmediata de Work, Changes, gates, Git y conversaciones nuevas. Una conversación persistida no cambia de Task al cambiar este contexto global. La baseline de verificación vigente es 128 tests TypeScript y 18 tests Rust.

ADE se ejecuta hoy verificada sólo en macOS, siendo Windows y Linux objetivos declarados según [SPEC-cross-platform-support](SPEC-cross-platform-support.md#platform-boundary). La aplicación ofrece una shell desktop Tauri con navegación lateral única y ordenada: `Projects`, `Agents`, `Version control`, `Context` y `Editor`. `Projects` reúne el catálogo, el Project activo y sus Tasks, de modo que `Tasks` no ocupa una entrada propia; la topbar no lleva breadcrumb. El runtime y los servicios permanecen como infraestructura transversal consumida por Agents, Work, terminal y los estados del shell, sin ocupar una entrada de navegación independiente. `Projects` mantiene un catálogo mínimo: lista y selección de carpetas Git o No Git, alta, retirada del seguimiento sin tocar el disco, título del Project activo y cuatro métricas compactas; no duplica Task workbench ni actividad. `Editor` recibe automáticamente los ficheros seleccionados desde Explorer. `Agents` ofrece sesiones persistidas por Project, selección de OpenCode/Codex/Claude Code, transcript y composer con permisos por turno y selector de modelo dependiente del provider; `Provider default` evita enviar overrides y los alias concretos se conservan sólo en memoria por conversación. Su superficie primaria se limita al rail y la conversación central para preservar espacio de lectura. El rail muestra sólo el Project activo, agrupa las conversaciones por Task y `General`, y persiste `projectId` y título para no depender de una agrupación meramente visual. El cambio de Project descarta respuestas asíncronas de prompts del contexto anterior y el sidecar rechaza lectura o borrado cruzado. El rail permite borrar conversaciones guardadas mediante una acción accesible que abre un diálogo modal `Delete`/`Cancel`; el borrado elimina la sesión y sus mensajes de SQLite, pero no archivos ni artefactos del Project. La implementación sigue [chatgpt-desktop-agents-audit](../knowledge/chatgpt-desktop-agents-audit.md) y [ADR-0029](../adr/0029-chatgpt-inspired-agent-workbench.md): conserva el thread sin tercera columna y mantiene modelo/provider sin falsear la reanudación entre runtimes. El Explorer mantiene como hint la rama del archivo activo y puede convertirse en un árbol completo; la búsqueda muestra ficheros directamente, añade una ruta relativa legible para distinguir homónimos, mantiene el input responsivo con índice normalizado, debounce y spinner de carga, y al seleccionarlos restaura la rama breadcrumb. La lupa junto a `Explorer` enfoca ese filtro. Ambos cambios tienen transición fluida. El lateral tiene un divisor vertical redimensionable por pointer o teclado hasta un máximo responsive de 720 px y conserva su ancho por Project. La topbar muestra el Project y, cuando aplica, branch Git activos; sus menús permiten cambiar entre Projects registrados y ramas locales, refrescando el contexto sin force checkout. La identidad del Project activo se conserva en un único estado del shell, por lo que snapshots y respuestas asíncronas no pueden restaurar el nombre del fixture inicial en topbar, breadcrumb, Projects, Editor ni paneles dependientes. El tema claro/oscuro se alterna desde la esquina superior derecha y se conserva entre sesiones.

El dock inferior expone tabs de terminal `portable-pty` persistentes, redimensionables y confinados a la raíz del Project. Cada tab conserva su proceso y superficie `xterm.js`; cambiar de tab no mezcla salida y cerrar uno detiene sólo su sesión. `Terminal.onData` reenvía directamente cada secuencia al PTY y `Terminal.onResize` sincroniza filas y columnas. El shell real conserva prompt, historial y completado, mientras xterm.js interpreta ANSI, cursor, borrado, color y pantalla alternativa, por lo que los prompts interactivos de Claude siguen siendo navegables sin campo HTML ni heurísticas de ADE. `Version control` adopta la jerarquía operativa de GitHub Desktop: `Changes` abre por defecto con filtro de ficheros, lista compacta y diff dominante; `History` incorpora filtro y separa lista de commits, ficheros y diff. En `Changes` el working tree y el diff usan dos paneles reales; en `History` las columnas auxiliares se colapsan de forma independiente con restauración accesible desde las cabeceras, y las líneas largas del diff se adaptan en tiempo real al ancho disponible. En ambas tabs las columnas auxiliares usan el mismo control de contracción, con idéntico icono, posición y animación. `Commit` sólo crea el commit local; `Push origin` y `Fetch origin` son acciones independientes que se ejecutan directamente, y `Push origin` se habilita cuando el repositorio tiene commits que el remoto no ha visto, los creara ADE o no. El estado remoto compone commits pendientes de empujar y cambios locales, `History` marca los commits no empujados, y las operaciones Git menos frecuentes quedan en `Repository actions`, plegable dentro de Version control. Las confirmaciones de acciones destructivas usan diálogos propios de la shell, porque el webview no responde a los prompts nativos del navegador. La topbar conserva el contexto global de Project y branch. La baseline de verificación actual es 128 tests TypeScript y 18 tests Rust. El `.app` macOS se empaqueta y se ha arrancado manualmente; el smoke gráfico automatizado sigue pendiente. `Projects` permite añadir y retirar del seguimiento carpetas Git o No Git sin tocar sus ficheros, y la selección de ficheros abre ahora dentro de ADE en `Editor`, definido en [SPEC-file-workspace](SPEC-file-workspace.md#product-contract), con edición, guardado y descarte acotados al Project.

La shell mantiene el contexto Git en la topbar para orientación global, pero reserva el panel operativo `Git workspace` exclusivamente a `Version control`; las demás vistas no duplican su estado ni sus acciones.

La paridad operativa de `Version control` con GitHub Desktop está implementada según [ADR-0028](../adr/0028-github-desktop-version-control-parity.md): `Changes` prioriza working tree y diff, `History` prioriza commit, ficheros y diff, y Project/branch, commit local, push y fetch conservan responsabilidades visibles y separadas. Comparación entre ramas y staging por línea siguen fuera del corte actual.

La iteración de hardening de shell elimina chrome simulado: no se renderizan tareas fixture, estado de salud, identidad local, notificaciones ni ayudas sin fuente/acción. `Work` comunica carga o vacío real y abre cada Task mediante control de teclado accesible. El grafo documental se limita a `Context`; las tabs `History`/`Changes` completan el patrón ARIA y navegación de teclado. La ventana Tauri abre a 1180 × 780 px, fija mínimo 900 × 640 px y el límite reactivo del lateral preserva 580 px de workbench. Monaco, sus contribuciones y Prettier se cargan bajo demanda para no penalizar el primer render; CodeMirror sigue siendo el motor inmediato de la ruta principal. La decisión de editor se actualiza en [ADR-0023](../adr/0023-code-editor-and-formatting.md).

## Current v0.4 slice

La vista `Editor` es una superficie fija y exclusiva de código: no muestra los paneles auxiliares de Git, agentes ni documentación. La terminal nativa sí permanece como dock transversal del shell y sigue disponible al cambiar de vista.

El layout del Editor aplica una densidad específica de workbench: reduce el padding heredado de las vistas generales y calcula la altura del área de código con el espacio disponible sobre el dock de terminal, evitando márgenes muertos sin convertir el editor en una superficie ilegible.

El Editor usa una interfaz común con CodeMirror 6 como motor principal y Monaco Editor como fallback selectivo. CodeMirror cubre los lenguajes oficiales incorporados y Monaco amplía el resaltado a C, C#, Go, Dart, Dockerfiles, Elixir, F#, GraphQL, Kotlin, Lua, Objective-C, Perl, PowerShell, Protocol Buffers, R, Ruby, Scala, Shell y Swift. Ambos motores se eligen por extensión sin cambiar la superficie ni el contrato de edición. Prettier MIT mantiene el formateado explícito de los lenguajes compatibles. Su contrato detallado y sus límites están en [SPEC-file-workspace](SPEC-file-workspace.md#product-contract) y la decisión en [ADR-0023](../adr/0023-code-editor-and-formatting.md).

La slice v0.4 implementa [SPEC-file-workspace](SPEC-file-workspace.md#product-contract): el fichero de texto seleccionado aparece dentro de ADE en `Editor`, con superficie completa, lectura y escritura Tauri autorizadas, estado dirty, `Save`, `Discard`, límite de 2 MiB y apertura externa únicamente mediante una acción explícita. La superficie selecciona CodeMirror o Monaco según la extensión y conserva el mismo contrato de edición. `Projects` permite registrar carpetas Git y No Git desde el selector nativo de macOS. `Agents` mantiene el rail de sesiones y la conversación como superficie única de trabajo, sin un inspector lateral permanente. El cambio de Project conserva la identidad activa en toda la shell y descarta únicamente el documento seleccionado si queda fuera de la nueva raíz. No se adelanta un editor completo ni una integración LSP.

## Scope boundary

Este nexus cubre MVP, v0.2 y v0.3 cerradas, además de la slice v0.4 de editor interno y sus refinamientos de shell. AgentMemory, ASK como dependencia, browser automation, cloud, sync realtime, colaboración multiusuario y productización siguen fuera. Los worktrees entran en v0.3 sólo como aislamiento Git local.

## MVP contract

El modo `standard` cubre: abrir repositorio, crear Task, resolver contexto, ejecutar Implementer, capturar ChangeSet, build/tests, resumen, Reviewer independiente, findings, re-review, reconciliación documental, aprobación humana y commit. El modo `quick` sirve para cambios pequeños; `recovery` permite reentrar tras nueva evidencia o un fallo. Ningún modo puede omitir los invariantes definidos en [SPEC-development-workflow.md#gates-and-invariants](SPEC-development-workflow.md#gates-and-invariants).

Los cuatro spikes previos a UI significativa son: integración OpenCode y eventos; Implementer/Reviewer; resolución e impacto documental; y runtime local con logs y verificación.

## v0.2 contract

La siguiente iteración está definida en [SPEC-v0.2.md](SPEC-v0.2.md): revisión y gates visibles, evidencia de runtime persistida, servicios locales declarados y navegación contextual de Tasks. Su orden de entrega es `runtime-evidence → task-detail-read-model → review-gates-ui → local-services → rehydration-smoke`. Cloud, worktrees, colaboración, multiagente complejo y commits autónomos continúan fuera de alcance.

## Deferred decisions

Estas decisiones no bloquean las releases cerradas y se mantienen para iteraciones posteriores: esquema SQLite definitivo; retrieval y embeddings; checkpoints; automatización de commits; evolución del esquema `.ade/`; enforcement completo de taxonomía documental; memoria/equipos; licensing y pricing; editor completo; `.dmg`; cloud y colaboración realtime.
